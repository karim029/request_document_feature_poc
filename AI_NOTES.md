# AI notes

## Where I used AI
I used Claude as a mentor and as a code generator. I made the design decisions, and I read, ran and checked what it produced.

- **I wrote or decided myself:** the plan for the upload path (a conditional update, a version, an event row), the choice to add a status index after my own tests, the checks that caught two suspicious results, and every measurement run.
- **The AI wrote, and I reviewed and ran:** the review method and its unit tests, the `seed:large` script, the k6 and write-cost scripts, the dashboard and bulk create code, the integration tests, the CI workflow, and first drafts of the documents. I changed the code on purpose to check that each test fails when it should.
- **The AI explained concepts** (indexes, `EXPLAIN`, isolation levels, keyset pagination), and I made my own notes from them.

## Where it was wrong, and how I caught it
1. **A race the AI's code missed.** The review method it wrote returned 400 instead of 409 to some of the requests that lost a race. The cause was MariaDB's default isolation level: the losing request read the row again from an old snapshot, saw the old version, and blamed the status. My parallel integration test caught it (20 calls at once: one 200, ten 409, nine something else). The fix was running those transactions at READ COMMITTED.
2. **A wrong diagnosis.** When the inbox was slow under load, the AI said it was a full table scan. `EXPLAIN` showed it was an index lookup, and `ANALYZE FORMAT=JSON` showed the real cause: the database chose an index without `createdAt` and read 13,833 pages per query instead of 91.
3. **A wrong explanation of the dashboard.** It said the temporary table and the sort were the cost of the top clients query. `ANALYZE` showed the sort took 0.06 ms and the cost was about 10,000 page reads from the table, so the fix was to read less from the table.
4. **A wrong prediction and wrong code.** It predicted the overdue filter would be slow (it was not) and that a bigger memory cache would help only a little (it helped 17 times). It also wrote `@Headers('x-actor-id', ParseIntPipe)`, which does not exist, and the compiler showed it.
5. **A gap I found by asking a question.** I asked whether `POST /requests` needed protection from concurrency. A plain insert has nothing to overwrite, but looking at the code showed that the endpoint wrote no first history event and recorded no actor, unlike bulk create. The AI had written the event rule and bulk create but had not checked the older single create. I fixed it by writing the request and its first event in one transaction, with the actor from the header.
6. **A strict review before submitting.** A week before the review I asked Claude Code, in read-only mode, to review the whole repository strictly. It found a real bug: the dashboard turnaround query paired every upload with every decision of a request, so the average was wrong after a rejection and a re-upload. I fixed it, with a test that fails on the old query. It also found missing length limits (a long title or rejection reason returned 500), which I fixed, and about a dozen sentences in my documents that the code did not support, which I corrected. It was wrong about one thing: it called orphaned upload files a bug. I checked by hand, and the framework already removes the file when validation fails, so only files replaced by a re-upload stay on disk, as a documented limitation. A final read-only check found one more contradiction (a long description returned 500), which I also fixed. I reviewed every diff and pushed the changes myself.

## How I check things
Before most commits I run build, lint, unit tests and the integration tests, and I read `git diff` (a few documentation edits were made in the GitHub editor). I repeat measurements, and I do not trust a result that contradicts how the system works: a write test that did not repeat when I reversed the order, and a cached dashboard run identical to the uncached one (the cache was off because of a mistake in `.env`). A drift check with `migration:generate` caught a typo in an index name.
